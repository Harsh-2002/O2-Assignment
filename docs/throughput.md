# Throughput validation

The assignment asks for approximately 5 GB/hour of logs and 5 GB/hour of metrics. The generator runs for five minutes per pod. Two pods share the load; the four-minute overlap from 2026-09-11 21:00:00 to 21:04:00 UTC is the measurement window, excluding startup and shutdown boundaries.

## Results

Measured window: 2026-09-11 21:00:00–21:04:00 UTC (02:30–02:34 IST on September 12).

| Signal | Accepted records | JSON bytes | Decimal GB/hour |
| --- | ---: | ---: | ---: |
| Logs | 229,322 | 333,609,143 | 5.0041 |
| Metrics | 1,171,200 | 333,008,801 | 4.9951 |

Both are within 0.1% of 5 GB/hour on the measurement basis described below. This was a four-minute steady measurement, not an hour-long endurance test.

Across the entire finite run, 1,464,000 metric samples were accepted, matching two pods × 2,440 samples × 300 batches. Logs totalled 292,401 versus 286,200 nominal records; rollout overlap added records outside the nominal generator count. Log batching also shifts receive timestamps across window boundaries. The reported rates count actual accepted rows rather than assuming exact source counts.

Both measured pods reported zero restarts. A live resource snapshot showed approximately 41–45 millicores and 36–37 MiB memory per pod. The saved log snapshot contains no ingestion errors. Sources completed and the Deployment was scaled to zero after evidence collection.

## What is measured

The primary measurement is the uncompressed JSON representation of records accepted by OpenObserve, filtered by run_id `load-20260911`. SQL sums serialized field lengths over that exact window. All generated strings are ASCII and contain no characters needing JSON escaping, so character and byte lengths are equal. This reconstruction includes OpenObserve's returned metadata fields. It is not compressed HTTP traffic, Prometheus protobuf size, or a verified billable-ingestion counter.

OpenObserve's stream summary statistics lagged ingestion during testing. They are saved alongside query results for transparency, but are not used to claim the measured rate. A strict interpretation requiring the provider's billable-byte counter would need a settled before/after counter measurement.

Rate in decimal GB/hour = accepted JSON bytes / window seconds × 3600 / 1,000,000,000.

## Generator

Each pod emits 477 logs and 2,440 metric samples per second for 300 batches. Together that is 954 logs/sec and 4,880 samples/sec. Logs carry a fixed synthetic message and rotate among three services and severity levels. Metrics use random latency values and a bounded set of 4,880 series across both pods, identified by pod name and sequence. Series are reused each second.

Vector's demo_logs sources feed remap transforms, which expand each tick into a batch. log_to_metric converts metric seeds into gauges, sent through Prometheus remote write. Each metric batch flushes independently to avoid combining consecutive samples for the same series. Internal Vector metrics use a separate sink and are excluded from the synthetic stream measurement.

The initial calibration exposed unsupported VRL syntax and inefficient array copying. The final configuration uses map_values and was fully compiled with `vector validate --skip-healthchecks` before deployment. A 15-second calibration accepted all 14,310 logs and 78,000 metric samples generated by one pod.

## Reproduce

Run these from the repository root after creating the namespace and local Secret:

```bash
kubectl -n observability scale deployment/vector --replicas=0
kubectl apply -f kubernetes/load-test.yaml
kubectl apply -f kubernetes/load-deployment.yaml
kubectl -n observability rollout status deployment/vector --timeout=180s
kubectl -n observability get pods
kubectl -n observability top pods
```

`load-test.yaml` replaces the same vector-config ConfigMap used by development. `load-deployment.yaml` sets two replicas and adds POD_NAME through the Downward API. Do not apply the whole Kubernetes directory: choose either the development pair or the load-test pair explicitly.

The sources stop after 300 batches, but the pods continue exporting internal metrics. Stop the pods after drain and verification:

```bash
kubectl -n observability scale deployment/vector --replicas=0
```

A container restart resets the finite source count. Watch restart counts during testing and stop the Deployment if a pod restarts. Use a fresh run_id for a new measurement and update the dashboard run filter accordingly. Do not leave the cluster running after evidence collection.

Evidence files contain API query results, pod state, resource usage, and logs. The dashboard JSON exports include the measured-rate panels. Select the test's absolute time range when viewing data after teardown.
